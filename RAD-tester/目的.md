## 1. 目的
Windows 11 環境において、最新の **.NET 10 (net10.0)** を基盤とし、追加のサードパーティ製ライブラリをインストールすることなく、**TLS 1.3** や **PEM 形式秘密鍵の直接読込** に対応した RADIUS / RadSec 認証テストツールを提供する。

## RADIUS / 802.1X 認証概要
IEEE 802.1X / RADIUS では、**Supplicant（端末）**、**Authenticator（AP や Switch）**、**認証サーバー（RADIUS サーバー）** の 3 者で認証を行います。

- **トンネル型 EAP 認証（PEAP / EAP-TTLS / EAP-TLS / EAP-FAST / EAP-TEAP）**:
  - Supplicant と RADIUS サーバー間で TLS 暗号化トンネルを接続します。
  - Authenticator (AP / Switch) は中継するだけで、パスワード等の資格情報を見られることはありません。
  - 認証完了後、RADIUS サーバーから Authenticator に結果 (`Access-Accept`) や暗号化鍵（WPA/WPA2/WPA3 用の暗号鍵生成キー）などが伝えられ、通信が許可されます。

- **非トンネル型 EAP 認証（EAP-GTC / EAP-MD5 など）**:
  - TLS トンネルを張らず、EAP フレーム上で直接チャレンジ・レスポンスやトークン情報をやり取りします。

- **非 EAP 認証方式（PAP / CHAP / MS-CHAPv2）**:
  - トンネルを張らず、RADIUS パケット内の属性（`User-Password` や VSA など）に直接認証データを格納してやり取りするクラシックな認証方式です。

### プロトコル進行における通信方向（Flow）の表示規則
本ツールでは、画面（CLI および GUI）上の **「プロトコル進行状況 (Flow)」** において、**常に「RADIUS サーバーを右側」に配置** して通信の送受信関係を直感的に把握できるようにしています。

| 通信方向の表記 | 送信元 --> 送信先 | 該当パケット・処理内容 |
|---|---|---|
| `Supplicant --> RADIUS` | 端末 --> RADIUS | EAP 認証時のリクエスト（`Access-Request`: EAP-Response/Identity, EAP-Response/TLS, Inner 資格情報） |
| `Supplicant <-- RADIUS` | 端末 <-- RADIUS | EAP 認証時のチャレンジ（`Access-Challenge`: EAP-Request/TLS, サーバー証明書フラグメント, Inner チャレンジ） |
| `Authenticator --> RADIUS` | AP/Switch/NAS --> RADIUS | 非 EAP 認証（PAP, CHAP, MS-CHAPv2, MAC 認証）時のリクエスト（`Access-Request`） |
| `Authenticator <-- RADIUS` | AP/Switch/NAS <-- RADIUS | **認証の最終結果（`Access-Accept` / `Access-Reject`）**。<br>※RADIUS サーバーが AP/Switch に対してポート通信許可、暗号化鍵（MS-MPPE-Key）、VLAN 割り当てを通知 |
| `Supplicant --> RADIUS` / `Supplicant <-- RADIUS` | 端末 <--> RADIUS | `Status-Server` 生存確認パケット、UDP ソケット初期化、TCP コネクション確立 |
| `Supplicant <--> RADIUS` | 端末 <--> RADIUS | RadSec (RFC 6614) における TLS 1.3 / 1.2 トランスポートハンドシェイク |
| `Supplicant --> DNS` | 端末 --> DNS | 対象サーバーホスト名の名前解決（A / AAAA レコード検索） |

#### 802.1X EAP 認証時のシーケンス例（RADIUS を右側に配置）
```
[Supplicant (端末)]        [Authenticator (AP/Switch)]        [RADIUS サーバー]
        │                              │                              │
        │=== EAP-Response/Identity ===>│=== Access-Request ==========>│ (Supplicant --> RADIUS)
        │<== EAP-Request (TLS Start) ==│<== Access-Challenge =========│ (Supplicant <-- RADIUS)
        │=== TLS Client Hello ========>│=== Access-Request ==========>│ (Supplicant --> RADIUS)
        │<== TLS Server Hello, Cert ===│<== Access-Challenge =========│ (Supplicant <-- RADIUS)
        │                              │                              │
        │     [ TLS トンネル確立 & 内部認証 (MS-CHAPv2 / TLS 等) ]     │
        │                              │                              │
        │                              │<=== Access-Accept ===========│ (Authenticator <-- RADIUS)
        │<== EAP-Success ==============│     (ポート開放・鍵/VLAN適用)│
```
> **なぜ `Access-Accept` は `Authenticator <-- RADIUS` なのか？**
> IEEE 802.1X では、端末と AP 間の物理ポートや Wi-Fi ポートは最初「未認証（ブロック状態）」になっています。認証完了時に RADIUS サーバーが最終的な `Access-Accept` を **Authenticator（AP や Switch）宛て** に送信することで、Authenticator はパケット内に含まれる WPA 暗号鍵（MS-MPPE-Recv-Key / Send-Key）や VLAN ID を自身に適用し、ポートの通信遮断を解除します。そのためプロトコルの進行上、最終結果は **`Authenticator <-- RADIUS`** となります。


### トランスポート層（伝送路）の暗号化：RadSec との関係
上記が「認証方式（端末〜サーバー間の資格情報保護）」であるのに対し、**RadSec (RFC 6614)** は **「伝送路（AP/Switch 〜 RADIUS サーバー間）」を保護するトランスポート暗号化技術** です。

- **従来の RADIUS (UDP 1812)**:
  - 共有シークレットによる MD5 署名のみでパケットを送受信するため、拠点間 WAN やインターネット経由では盗聴・改ざんの危険（BlastRADIUS 脆弱性など）があります。
- **RadSec (TCP/TLS 2083)**:
  - AP/Switch と RADIUS サーバー間を **TLS 1.3 / 1.2（相互証明書認証）** でカプセル化します。
  - PAP や MAC アドレス認証のような非 EAP 方式であっても、インターネット経由で安全にクラウドアカウント認証を行えます。
  - トンネル型 EAP と組み合わせることで、端末〜サーバー間の認証情報と、拠点間ネットワーク伝送路の双方が二重に保護されます。

> **本ツール (`RadiusTest.exe`) の対応**:
> **「UDP 1812」** と **「RadSec (TLS 2083)」** の両方に対応しており、どちらのトランスポート上でも各種認証（PAP / CHAP / MS-CHAPv2 / EAP 各種）をテストできます。

## 3. 機能要件

### 3.1 RADIUS プロトコル基本機能（UDP / RFC 2865）
- **トランスポート**: UDP (デフォルトポート `1812`、変更可)
- **認証方式**:
  - **PAP** (RFC 2865): 共有シークレットによるパスワード暗号化 (`User-Password`)
  - **CHAP** (RFC 1994 / RFC 2865): チャレンジ・レスポンス方式 (`CHAP-Challenge` + `CHAP-Password`)
  - **MS-CHAPv2** (RFC 2759 / RFC 2548): Microsoft VSA (Vendor 311) による相互認証対応チャレンジ・レスポンス (`MS-CHAP-Challenge` + `MS-CHAP2-Response`、`MS-CHAP2-Success` 相互認証検証、`MS-CHAP-Error` エラー詳細解析)
- **リクエスト種別**: `Access-Request` / `Status-Server`（RFC 5997、生存確認用）
- **付与する属性**: `User-Name`, `User-Password`, `NAS-IP-Address`(IPv6 時 `NAS-IPv6-Address`), `NAS-Identifier`, `NAS-Port`, `Service-Type`, `Called/Calling-Station-Id`, `Message-Authenticator`(任意), 任意の追加属性（`-attr` / `-attrhex`）
- **応答の検証**: パケット長・Identifier・Response Authenticator・Message-Authenticator
- **タイムアウトと再送**: 受信タイムアウト・再送回数を指定可（再送は同一 ID/Authenticator）
- **Access-Challenge**: `State` 属性を保持し、対話入力した応答で再送信（最大 8 ラウンド）

### 3.2 RadSec（RADIUS over TLS / RFC 6614）＋クライアント証明書認証
- **トランスポート**: TCP + TLS (デフォルトポート `2083`)、`-radsec` で有効化
- **共有シークレット**: 既定値 `radsec`（RFC 6614）。`-secret` で変更可
- **TLS 1.3 ネイティブ対応**:
  - `-tls 1.3|1.2|1.1|1.0|auto`（既定 1.3 または auto。TLS 1.3 のモダン暗号スイートに対応）
- **クライアント証明書（相互 TLS）**:
  - **PEM 形式の直接読込**: `-cert client.crt -key client.key`（.NET 10 ネイティブ対応、PFX 変換不要）
  - PFX ファイルから読込 (`-cert client.pfx -certpass ...`)
  - Windows 証明書ストアから読込 (`-thumb` 拇印 / `-certsubject` サブジェクト、`-store`, `-storeloc CurrentUser|LocalMachine`)
  - 読込時に Subject / Issuer / 拇印 / 有効期間 / EKU を表示し、期限切れ・Client Authentication EKU 欠落を警告
- **サーバー証明書検証**:
  - 既定: OS の信頼ストアで検証
  - `-cacert ca.crt`: 指定 CA 配下のサーバー証明書のみ信頼（DER または PEM 形式、複数指定可）
  - `-nonamecheck`: 名前不一致を無視 / `-sni <name>`: SNI・名前検証に使うホスト名
  - `-insecure`: 検証無効（テスト専用、自己署名証明書受入、警告を表示）
- **TLS 情報の表示**: プロトコル（TLS 1.3 / 1.2 等）、暗号スイート、サーバー証明書チェーン、クライアント証明書提示有無、相互認証成否
- **TLS のみのテスト**: ユーザー名未指定の場合は TLS ハンドシェイクのみを実施（`Status-Server` も併用可）
- **TCP ストリーム処理**: RADIUS Length フィールドに基づくフレーム分割

### 3.3 EAP 認証方式（EAP-TLS / EAP-TTLS / PEAP / EAP-GTC / EAP-FAST / EAP-TEAP）
- **カプセル化 (RFC 3579)**: `EAP-Message (Type 79)` 属性への EAP パケット格納（253 バイト境界での自動分割と再構築）
- **EAP-NAK ネゴシエーション (RFC 3748)**: サーバーが初期提案した EAP Type（MD5-Challenge 等）に対して EAP-NAK (Type 3) を送信し、希望する EAP 方式へ自動ネゴシエーション
- **双方向メモリパイプストリーム**: .NET 10 `SslStream` を仮想パイプ経由で EAP パケット送受信ループに直結
- **TLS フラグメンテーション (RFC 5216 / RFC 5281 / RFC 4851 / RFC 7170)**: Flags（Length, More, Start）を用いた TLS レコードの自動分割送信およびサーバーからの複数フラグメント再構築
- **EAP-TLS (RFC 5216)**: クライアント証明書を用いた相互 TLS ハンドシェイク（EAP-Success / EAP-Failure 判定）
- **EAP-TTLS (RFC 5281)**: TLS トンネル確立後の Inner PAP 認証（Diameter AVP: User-Name + User-Password の暗号化送信）
- **PEAP (MS-PEAP / PEAPv0 / RFC 2759)**: 外側 TLS トンネル確立後の Inner EAP 認証。Inner Identity、Inner EAP-MSCHAPv2（OpCode 1 Challenge -> OpCode 2 Response NT-Response 24バイト暗号化送信 -> OpCode 3 Server Success / `S=...` 相互認証検証 -> OpCode 3 Success ACK）、および Result-TLV (Type 33) 応答による安全な認証ハンドシェイクの完了処理
- **EAP-GTC (Generic Token Card / RFC 3748)**: サーバーからのチャレンジプロンプト（`Password: ` 等）を受信し、ユーザーパスワードまたはトークン値をテキスト応答する直接認証方式（外側単体認証および PEAP 内側認証の両方に対応）
- **EAP-FAST (Flexible Authentication via Secure Tunneling / RFC 4851)**: Phase 1 TLS トンネル確立（Version 1 フラグ対応）＋ Phase 2 TLV コンテナ（Type 9 EAP-Payload、Type 10 Intermediate-Result、Type 12 Crypto-Binding 応答生成、Type 3 Result）による安全な多段階認証
- **EAP-TEAP (Tunnel Extensible Authentication Protocol / RFC 7170)**: 次世代トンネル型 EAP 認証（Type 55, Version 1）。Phase 1 で TLS トンネルを確立し、Phase 2 の TLV コンテナ（Type 2/17 Identity-Type、Type 9 EAP-Payload、Type 13/14 Basic-Password-Auth、Type 10 Intermediate-Result、Type 12 Crypto-Binding、Type 3 Result）を通じて同一トンネル内でのマシン認証・ユーザー認証の連鎖（Dual Authentication / Chaining）に対応

### 3.4 2段階の表示出力（概要とパケット詳細）

#### (1) プロトコル進行概要 (Protocol Flow Overview)
フェーズごとに時刻（ms）付きでリアルタイム表示し、最後に一覧サマリ（どこまで進んだか）を出力する。

| # | フェーズ | 内容 |
|---|---|---|
| 1 | `INIT` | パラメータ確認、証明書・秘密鍵読込 |
| 2 | `RESOLVE` | 宛先名前解決 |
| 3 | `CONNECT` | UDP ソケット準備 / TCP 接続 |
| 4 | `TLS` | TLS ハンドシェイク（RadSec のみ。UDP は N/A。TLS 1.3 / 1.2 対応） |
| 5 | `BUILD` | Authenticator 生成、パスワード暗号化、属性構築 |
| 6 | `SEND` | 送信（再送回数表示） |
| 7 | `RECV` | 受信待機・受信（RTT、ICMP Port Unreachable 検知） |
| 8 | `VERIFY` | 長さ・ID・Response Authenticator・Message-Authenticator 検証 |
| 9 | `RESULT` | `Access-Accept` / `Access-Reject` / `Access-Challenge` / エラー |

各フェーズは `OK / WARN / FAIL / N/A / 未到達` で表示。失敗時は原因のヒント（ファイアウォール、シークレット不一致、証明書不信頼、クライアント証明書拒否 等）を併記する。

#### (2) パケット詳細 (Packet Details)
送受信した各パケットを表示（`-brief` で非表示、`-nohex` で hex ダンプ非表示）。
- **ヘッダー**: Code(名称)、Identifier、Length、Authenticator
- **属性一覧**: Type 番号・属性名・長さ・デコード値（文字列 / IPv4 / IPv6 / 整数＋列挙名 / 16 進、Vendor-Specific はベンダー名＋サブ属性）
- **RAW HEX ダンプ**: 16 バイト区切り＋ASCII プレビュー

### 3.5 IPv6 トランスポート & NAS-IPv6-Address (RFC 3162)
- **IPv6 デュアルスタック接続**: RADIUS/UDP および RadSec (TLS) において IPv6 リテラルアドレス（`[::1]`, `[fe80::...%scope]`, `2001:db8::...`）およびホスト名解決時の AAAA レコード優先（`-6` / `-ipv6`）に対応。
- **RFC 3162 準拠の NAS IP 属性自動選択**: `-nasip` に IPv6 アドレスが指定された場合、従来の Type 4 (`NAS-IP-Address` - 4バイト) ではなく、自動的に Type 95 (`NAS-IPv6-Address` - 16バイト) を生成・送信。IPv4 アドレス指定時は Type 4 を送信。
- **角括弧トリムとスコープID処理**: CLI 入力時の `[fe80::...%scope]` 形式の自動パース、および TLS SNI 送信時の安全なスコープID分離処理。

### 3.6 クラシックスタイル GUI フロントエンド (Windows Forms)
- **高密度クラシックデザイン**: 余白やパディングを極力抑え、画面を広く占有しないコンパクトで視認性の高い Windows Forms UI（9pt BIZ UDPゴシック / BIZ UDゴシック / 等幅部 Consolas）。高DPI環境でも文字欠けの起きない最適化済みレスポンシブレイアウト。
- **シングルバイナリ両立**: 引数なしのダブルクリック起動または `-gui` 指定で GUI モード、引数指定時はコンソール CLI モードとして 1 つの `RadiusTest.exe` で両立。
- **フル機能対応の設定パネル（タブ分離型）**:
  - **「認証・接続設定」タブ**:
    - サーバー接続設定（ホスト、ポート、シークレット、RADIUS UDP / RadSec TLS ワンタッチ切替）
    - IPv6/IPv4 優先度切替（自動 / IPv6強制 / IPv4強制）
    - ユーザー認証設定（User, Password, 方式: PAP / CHAP / MS-CHAPv2, Status-Server 生存確認, Msg-Auth 付与 (Type-80)）
    - EAP 認証設定（EAP-TLS, EAP-TTLS, PEAP, EAP-GTC, EAP-FAST, EAP-TEAP, Outer Identity, MTU）
    - TLS・証明書設定（TLS 1.3 / 1.2、ファイル参照ダイアログ、Windows 証明書ストア参照ダイアログ、`-insecure` 自己署名受入、ホスト名検証スキップ）
  - **「オーセンティケーター属性」タブ**:
    - **オーセンティケーター (NAS) 属性設定 (RFC 2865 / 3162 / 3580)**:
      - 各属性の先頭にコンパクトな **小型トグルボタン `[ ON ]` / `[ OFF ]`** を配置。
      - **OFF 時**: ボタンおよび入力項目・ラベルがグレーアウト（無効化）され、パケットへの送信を抑止。
      - **ON 時**: ボタンがソフトグリーンに変化し、入力コントロールがアクティブ化。空欄の場合はデフォルト動作（自動検出など）で送信、入力時はその値で上書き送信。
      - `NAS-Identifier` (Type 32): ホスト名など (初期値: OFF)
      - `NAS-Port-Type` (Type 61): 接続方法（Wireless-802.11, Ethernet 等, 初期値: OFF）
      - `NAS-Port` (Type 5): 論理インターフェース番号 (初期値: OFF)
      - `NAS-Port-Id` (Type 87): ポート名、SSID (初期値: OFF)
      - `Called-Station-Id` (Type 30): APのMAC:SSID など (初期値: OFF)
      - `NAS-IP-Address` (Type 4): IPv4 NAS アドレス (IPv4時初期値: ON。空欄時はローカルIPv4自動設定、OFF時は送信抑止)
      - `NAS-IPv6-Address` (Type 95): IPv6 NAS アドレス (IPv4時初期値: OFF。ONにすることで IPv4 と IPv6 の **両方同時送信** が可能)
    - **任意追加属性 (カスタム RADIUS 属性)**:
      - 1行に1属性を入力（`Name=値` または `Type=値`、16進数は `0x...`）することで、任意の標準属性・ベンダー固有属性 (VSA) をパケットへ自由に追加可能。
  - **下部固定アクションボタン**: タブを切り替えても常時操作可能な「認証テスト開始 (F5)」「CLI 引数コピー」「ログクリア」ボタン。
- **プロトコル進行フェーズ表示 (ListView)**: 全 9 フェーズ（INIT, RESOLVE, CONNECT, TLS, BUILD, SEND, RECV, VERIFY, RESULT）の状態（OK/WARN/FAIL/SKIP）、通信方向（Flow）、経過時間、メッセージを行ごとに見やすく色分け表示（データ準備行: 淡ラベンダー、送信行: 淡ブルー、受信行: 淡グリーン、結果・検証: 淡ミント、警告: 淡黄、エラー: 淡赤）。
- **パケット属性ツリー & RAW 16進ダンプ**: 送受信された全パケットの一覧（上下可動スプリッター付き）、パケット内容の自動詳細解析サマリ（TLS Client Hello, Server Hello, サーバー証明書, Phase 2 暗号化データ, EAP-NAK, PAP/CHAP 等）、選択パケットの「向き (Flow)」および「詳細メッセージ」専用表示領域、属性一覧ツリーおよび Consolas 等幅フォントによる HEX ダンプビューアー。
- **TOTP / Access-Challenge 2要素認証ダイアログ**: サーバーからの Access-Challenge 受信時にモーダルダイアログを自動ポップアップし、TOTP ワンタイムパスワードの対話入力をサポート。
- **CLI コマンド生成機能**: GUI で設定した内容をワンクリックで CLI 引数文字列（`RadiusTest.exe ...`）としてクリップボードにコピー可能。

## 6. 制約・注意事項
- クライアント証明書・秘密鍵は **PEM 形式 (`.pem`, `.key`, `.crt`)**、**PFX (`.pfx`, `.p12`)**、および **Windows 証明書ストア** から直接読み込み可能（.NET 10 ネイティブ機能）。
- サーバー CA 証明書（`-cacert`）は DER / PEM の `.cer` `.crt` `.pem` に対応。
- Windows 11 の Schannel 上で TLS 1.3 をフルサポート。
- 検証済み:
  - ローカルモックサーバー: UDP 認証、RadSec 相互 TLS（PFX / 証明書ストア拇印 / `-cacert` / `-insecure`）、Status-Server、Reject、サーバー証明書不信頼、ICMP 到達不能の各ケースを確認。
  - 実機 FreeRADIUS (3.2.8 / Fedora on WSL):
    - **Status-Server**: UDP 1812 に対する生存確認（`Access-Accept` 応答 / RTT 0ms）確認。
    - **PAP / CHAP / MS-CHAPv2**: UDP 1812 に対する `Access-Request` 疎通、Response/Message-Authenticator 検証、および MS-CHAP-Error (`E=691`) 詳細エラー解析の完全動作を確認。
    - **RadSec (TLS 1.3)**: ポート 2083 に対する TLS 1.3 ネイティブハンドシェイク（暗号スイート `TLS_AES_256_GCM_SHA384`）の完全成功を確認。
    - **EAP-TTLS (RFC 5281)**: EAP-NAK ネゴシエーション、サーバー証明書チェーン（約3KB）のマルチフラグメント再構築、TLS トンネル確立、および Inner PAP 暗号化送信・FreeRADIUS 認証の完全動作を確認。
    - **EAP-TLS (RFC 5216)**: EAP-NAK ネゴシエーション、クライアント証明書（約1.2KB）のフラグメント分割送信、および TLS ハンドシェイク往復の完全動作を確認。
    - **PEAP (MS-PEAP / PEAPv0)**: EAP-NAK ネゴシエーション、TLS トンネル確立、Inner Identity 応答、Inner EAP-MSCHAPv2（NT-Response 24バイト暗号化送信、サーバー相互認証文字列 `S=...` の受信）、Result-TLV (Type 33) 承認、および最終 `Access-Accept`（MS-MPPE-Send-Key / MS-MPPE-Recv-Key 属性含む）の完全動作を確認。パスワード不一致時の `TLV failure code 2` による拒否検知も確認。
    - **EAP-GTC (RFC 3748)**: EAP-NAK ネゴシエーション、サーバーからのチャレンジプロンプト（`Password: `）受信、EAP-Response/GTC パスワード送信、および `Access-Accept` 承認の完全動作を確認（不正パスワード時の `Access-Reject` も確認）。
    - **EAP-FAST (RFC 4851)**: EAP-NAK ネゴシエーション、Version 1 フラグによる Phase 1 TLS トンネル確立、Phase 2 Inner Identity、Inner EAP-MSCHAPv2、Intermediate-Result TLV、Crypto-Binding TLV レスポンス生成、Result TLV 成功判定、および最終 `Access-Accept` の完全動作を確認（不正パスワード時の `Access-Reject` も確認）。
    - **EAP-TEAP (RFC 7170)**: EAP-NAK ネゴシエーション（Type 55, Version 1）、Outer Authority-ID (Type 1) 交換、Phase 1 TLS トンネル確立（TLS 1.2 / TLS 1.3）、Phase 2 Inner Identity、Basic-Password-Auth、Identity-Type (Type 2 / Type 17)、Intermediate-Result TLV (Success)、Result TLV (Success)、Crypto-Binding TLV レスポンス生成の一連のハンドシェイク送受信および FreeRADIUS 側の内部資格情報検証を確認。
  - IPv6 トランスポート & RFC 3162 検証:
    - **IPv6 UDP 通信**: Windows ホストから WSL 上の IPv6 UDP ソケット（`[::]:18125`）に対する `[fe80::215:5dff:feeb:8bde%78]` 経由での Access-Request 送信、および Access-Accept 応答受信・全9フェーズ完走（RTT 1ms）を確認。
    - **RFC 3162 NAS-IPv6-Address**: `-nasip 2001:db8::100` 指定時に Type 95（16バイト IPv6 アドレス）としてパケットが正しくエンコードされ、サーバー側で正常に受信・パースされることを確認。
    - **IPv6 RadSec (TCP)**: ポート 2083 に対する IPv6 TCP コネクション確立（`CONNECT [ OK ]`）を確認。

## 7. 未実装・対象外の項目

### 7.1 EAP 認証方式
- 主要な EAP 方式（**EAP-TLS**, **EAP-TTLS**, **PEAP**, **EAP-GTC**, **EAP-FAST**, **EAP-TEAP**）の実装および実機検証が完了。
- **未対応・対象外プロトコル**:
  - **EAP-SIM (RFC 4186) / EAP-AKA (RFC 4187) / EAP-AKA' (RFC 5448)**:
    - **未対応（スコープ外）**。
    - **理由**: EAP-SIM および EAP-AKA は、物理 SIM/USIM カードハードウェア（GSM/UMTS 暗号アルゴリズム: Milenage, COMP128 等）や通信キャリアの移動体ネットワーク（HLR/HSS 認証センター）との直接連携を前提とした **通信キャリア Wi-Fi オフロード（Carrier Wi-Fi Offload / Passpoint）専用** の方式です。企業の社内 LAN / 802.1X / RADIUS 認証テストツールとしては利用されず、ハードウェア依存があるため未対応としています。

### 7.2 RADIUS 拡張・その他プロトコル
- **RADIUS Accounting (RFC 2866)**: `Accounting-Request` / `Accounting-Response`（ポート 1813）によるアカウンティング機能
- **CoA / Disconnect-Request (RFC 3576 / RFC 5176)**: サーバー主導の動的切断・属性変更リクエストの受信・処理

## 8. 異常系・過酷ファジング耐性テストの実行方法

本リポジトリには、実環境での破損パケットや悪意あるプロトコル攻撃（バッファオーバーフロー誘発、無限フラグメントによる DoS、BlastRADIUS 署名改ざん等）、および **RadSec (RADIUS over TLS 1.3 / 1.2)** の接続・証明書検証に対するクライアントの安全性を検証するための模擬サーバー（`mock_radius_server.py`）および自動テストスイート（`run_tests.py`）が同梱されています。

### 8.1 自動テストスイート（全 30 ケース）の一括実行

事前に `build.bat` で `RadiusTest.exe` をビルドした上で、以下のコマンドを実行すると、バックグラウンドでローカル模擬サーバー（UDP 1812 および RadSec TCP/TLS 2083）が自動起動し、全 30 ケースの異常系・過酷試験が約 4 秒で一括検証されます。

| | `valid_reject` (`-radsec -insecure`) | RadSec (TCP/TLS 1.3) での正常な Access-Reject ハンドリング | `1` |
| | `valid_accept` (`-radsec -cacert`) | `-insecure` なしで `-cacert` によるルート検証を通過し認証成功 | `0` |
| | `valid_accept` (`-radsec -tls 1.2`) | TLS 1.2 プロトコル指定での RadSec ハンドシェイクと認証成功 | `0` |
| | `valid_accept` (`-radsec` 未信頼CA) | 未信頼の自己署名証明書接続時に TLS ハンドシェイクを安全に拒絶して終了 | `3` |

### 8.2 単体モックサーバー（`mock_radius_server.py`）による手動・GUI テスト

特定の異常モードを指定して模擬サーバーを常駐起動し、GUI モード（`RadiusTest.exe`）や任意の CLI オプションから手動で接続試験を行うことも可能です。

```powershell
:: 1. 任意の異常モードを指定してモックサーバーを起動 (既定ポート: 1812, 共有シークレット: testing123)
python mock_radius_server.py --port 1812 --mode jumbo_packet_5000

:: 2. RadSec (TCP/TLS 2083) モードでモックサーバーを起動
python mock_radius_server.py --radsec --port 2083

:: 1回だけ応答して自動終了させる場合は --single を付与
python mock_radius_server.py --port 1812 --mode bad_msg_auth --single
```

モックサーバー起動後、別ターミナルまたは GUI 画面から `127.0.0.1`（ポート `1812`, Secret `testing123`）宛てにテストを実行することで、GUI の「プロトコル進行状況」や「パケット解析ツリー / HEX ダンプ」上で異常パケットがどのように可視化・警告されるかを直接確認できます。
